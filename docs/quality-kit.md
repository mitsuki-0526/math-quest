# 問題の品質の部品 — ほかのゲームで使うための手引き

- 作成日: 2026-09-30(先生の方針「今のゲームに影響が出ないなら、今後に活かせるほうを」)
- 仕組みの説明: [difficulty.md](difficulty.md)「問題の品質の 仕組み」

MathQuest で作った「問題を 作る → 検査する → 合格だけ 渡す → 不合格の 理由を 残す」仕組みと、先生の ○/× 判定を、次に作る学習ゲームでも使えるように、**持っていける部品** と **このゲームだけの調整** に分けてある。

## 1. 持っていけるもの

| もの | 場所 | 中身 |
|---|---|---|
| 問題の形式と 判定 | `src/math/template.ts` ほか `src/math/` | 問題の 型(`Problem`)、答えの 判定(数・分数・式・素因数分解・選択)、数式の 読み取り、図(`figure.ts`) |
| 品質の 仕組み | `src/math/quality/` | 仕様(`spec.ts`)・数学の 検査(`mathValidator.ts`)・Judge(`judge.ts`)・重複(`duplicateChecker.ts`)・不合格の 理由(`rejectReason.ts`)・ログ(`generationLog.ts`) |
| 学年・単元の 決まり | `src/math/quality/rules/curriculum.ts` | 学習指導要領と 先生の 方針。**出題タイプの 名前ではなく 単元で 当てる** ので、同じ 単元なら そのまま 効く(例: 絶対値の 記号は 使わない、文字と式の 計算で 分母に 文字を 出さない、1 年は 1 文字の 式だけ) |
| 1 問ずつ ○× 判定の 中心 | `src/math/quality/judging.ts` | 判定の 列の 作り方、ID から 問題を 作り直す、コピー用の 文 |
| 判定の 記録 | `quality/judgments.jsonl` | 先生の ○/× と 理由(問題・答え・単元・★)。**個人情報なし**。次の ゲームでの 手本・AI の 下見の 一致率を 測る 材料 |
| 道具 | `scripts/quality-report.mjs` `scripts/review-import.mjs` `scripts/review-export.mjs` | 品質レポート・判定の 取りこみ(記録に 足す)・一括判定の CSV |

`src/math/` は ゲームの コード(`@/data` `@/engine` `@/ui` `@/assets`)を 一切 使わない。`tests/boundary.test.ts` が 守っている。

## 2. 持っていけないもの(ゲームごとに 作る)

| もの | このゲームでの 場所 | 理由 |
|---|---|---|
| ★ ごとの 数の 範囲(仕様) | `src/data/grade1/specs.ts` | 「最初の ステージは ★1 まで」など、ゲームの 進み方に 合わせて 決めている。**根拠(source)は 持っていける 知識** なので、新しい 仕様を 決めるときの 参考に する |
| 1 問だけの ×(先生の 判定) | `src/data/grade1/rejected.ts` | 特定の 問題(キー)に 結びついている |
| ゲームだけの ルール | `registerJudgeRules()` で 登録 | 例: 「ボス戦では 〜」のような 置き場所の 決まり |
| 地点ごとの ★ の 上限・道中の ★3 の 数 | `src/data/grade1/chapters.ts`・`config.ts` | ゲームの 作り |
| 判定画面の 見た目 | `src/ui/scenes/JudgeScene.tsx` | Preact の 画面。ゲームの 送信(`api.review`)・場面の 切りかえに つながっている。中心は `judging.ts` なので、画面は 作り直しても 小さい |

## 3. 新しい ゲームで 使う 手順

1. `src/math/` を 持っていく(2 つめの ゲームを 作るときに、共通の パッケージに 切り出すのが よい)
2. 問題は **同じ 形式** で 作る。数学の 検査が 前提に していること:
   - 解説の 最後の 行に「答え」と 正解の 数を 書く(`\text{答え: } -5`)
   - 問題文の 平文(`promptText`)に 数を そのまま 書く(範囲の 検査が 読む)
   - `key` は 問題ごとに 一意、`verify` は 別の 計算方法の 式(テストで 照合)
   - 「よくある まちがい」(`mistakes`)と 教科書の 手順の 解説を 付ける
3. ゲームの 仕様(`registerSpecs`)と ゲームだけの ルール(`registerJudgeRules`)を 登録する
4. `npm run quality:report` で 品質の 不合格が 0 に なるまで 直す(学年・単元の 決まりは 最初から 効いている)
5. 先生に「1 問ずつ ○× 判定」を お願いする。**新しい 形の 問題だけ・数十問から**。同じ 単元の 記録(`quality/judgments.jsonl`)が あれば、前の ゲームで × に なった 形を 先に 避けておく
6. × の 理由を まとめて(`npm run review:import`)、持っていける 決まりは `rules/curriculum.ts` に、ゲームだけの ことは そのゲームの データに 書く

## 4. AI(LLM)に 問題文を 作らせる 場合

問題文の 自然さを AI に 任せる ときも、**数と 答えは プログラムで 作り、AI の 出力は 同じ 形式(問題文・答え・解説を 分けた JSON)で 受け取る**。そうすれば 同じ 検査に かけられる。AI に 問題を 判定させる(下見)ときは、先に `quality/judgments.jsonl` の 先生の 判定と 一致率を 測り、十分 高いときだけ 使う(自分で 作って 自分で 確かめる 危うさを 避けるため)。

## 5. 精度に ついて

- **数学の 検査・学年と 単元の 決まり** … そのまま 持っていける(問題の 形式が 同じなら)
- **先生の 判定から 作った 調整** … そのままでは 持っていけない(特定の 問題の 形・★・ゲーム内の 置き場所に 結びつく)。記録を 手本に して、新しい 形だけを 少し 判定して 取りもどす
- **今のゲームでの 結果**(品質の 不合格 0 件)は、今の 問題の 作り方での 数字。新しい ゲームでは `quality:report` で 確かめ直す
