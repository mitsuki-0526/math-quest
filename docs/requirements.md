- 作成日: 2026-09-19 / 最終更新: 2026-09-20
- ステータス: 承認済み(2026-09-20)
- 関連文書: [シナリオ設計書](scenario.md) / [設定資料](setting.md) / [台本](script/) / [画面モック](mock/screens.html)

## 1. 目的・背景

### 1.1 なぜ作るか

中学数学(1〜3年)の計算練習を、RPGの文脈(物語・成長・戦闘)の中で **生徒が自分から繰り返し取り組む** 形にしたい。単元ごとのドリルは既にあるが、「続きが気になるから今日もやる」という継続動機が弱い。

### 1.2 現状と前回の教訓

前回の試作 `math_go/計算ライド`(vanilla JS + Canvas、約300行)は「単元を選んで解くドリルに敵の絵を付けた」段階で止まり、以下の理由で断念した。

| 前回の壁 | 今回の対策(設計原則) |
|---|---|
| 画像・音などの素材制作で詰まった | **素材なしで全画面が成立する**設計にする。絵文字・図形のプレースホルダで先に全部動かし、AI生成の静止画を後から差し替える。アニメーションは素材に求めず CSS で行う |
| RPGロジックが肥大化して収拾がつかなくなった | **データ駆動**にする。シナリオ・敵・問題テンプレート・アイテムは全てデータ、エンジン(戦闘・マップ・会話)は小さく固定。マップは「歩き回る」ではなく **ノード式** |
| (共通) 全体を一気に作ろうとした | **縦切り開発**。「第1章が最初から最後まで遊べる」を最初のマイルストーンにし、章を増やす形で広げる |

### 1.3 成功の定義

1. **1年生版**が、自習時間・家庭学習で生徒が個人で進められる状態で完成し、授業に投入できる(最優先)
2. 2年・3年版が、同じエンジン・同じデータ形式のまま「章データとシナリオを足す」だけで作れる
3. 3学年を通して一本の物語になっている(途中の学年から始めても困らない)

## 3. ユースケース

| # | シナリオ | 頻度 |
|---|---|---|
| UC1 | **初回開始**: クラス・出席番号を選び、自分で合言葉を決める → 主人公の名前を入力 → プロローグ会話 → 第1章の村へ | 生徒1人1回 |
| UC2 | **空き時間の5分**: 「つづきから」→ ワールドマップで次のノードを選ぶ → 戦闘3回(1ノード) → 自動セーブ → 閉じる。ノードの途中で閉じても、次回はノードの最初から | 週数回 |
| UC3 | **家庭で15分**: ノードを2〜3個進める → 村で装備を買い宿で回復 → 章ボスに挑戦 → 章クリアイベント | 週1〜2回 |
| UC4 | **復習**: 村の「復習の泉」で、自分が間違えたタイプの問題を優先出題で解く(経験値・ゴールドは通常より少なめ) | 随時 |
| UC5 | **教師が章を解放**: 授業でその単元を終えたら、スプレッドシートの `unlock` シートで クラス × 章 にチェック → 生徒の次回起動時に反映 | 単元ごと |
| UC6 | **教師が進捗を見る**(want): スプレッドシートの集計シートで、クラス全員の章進捗・単元別正答率・最終プレイ日を見る | 週1回 |
| UC7 | **合言葉を忘れた**: 生徒が申告 → 教師が `students` シートでリセット → 生徒が再設定 | まれ |
| UC8 | **学年が上がる**(2年版以降): 2年版を起動 → 1年版のセーブがあれば引継ぎ(レベル・称号・仲間) → なければ「これまでのあらすじ」を見て標準ステータスで開始 | 年1回 |
| UC9 | **教師が動作確認**: 教師用のテストアカウント(全章解放)で、任意の章・ボスにすぐ飛べる | 随時 |

**規模**【仮】: 1学年 最大 200人、1人1日 50問程度 → 問題単位のログは 1日1万行になりうる。スプレッドシートの上限を考え、**問題単位のログは保存せず、セーブデータ内に単元別の集計(出題数・正答数・苦手タイプ)を持つ**。1生徒=1行 を原則にする。

- Google アカウント連携、氏名の保存

## 6. 非機能要件

### 6.1 データ保存
- 保存先: 教師のGoogleアカウントの スプレッドシート(GAS Web アプリ経由)
- シート構成(案): `students`(クラス, 番号, 合言葉ハッシュ, セーブJSON, 更新時刻) / `unlock`(クラス × 章) / `config`(制限時間などの調整値) / `summary`(F71, 数式で展開)
- 合言葉は平文で保存しない(ハッシュ+ソルト)。教師のリセットは「空にする」操作
- 個人情報は クラス・出席番号・主人公名(ニックネーム)のみ。実名は保存しない
- セーブJSONは版番号を持ち、旧版からの移行処理を用意する

### 6.2 通信・可用性
- 通信失敗時もプレイ継続(ローカルキャッシュ)。復帰時に自動同期。未同期状態を画面に表示(F97)
- GAS の実行制限(同時実行・1日あたりの実行時間)を考慮し、保存はノード完了などの区切りでまとめて1回
- 授業で35人が同時に起動しても失敗しないこと(GAS 側は軽い読み書きのみ)

### 6.3 性能
- 初回表示 3秒以内(学校回線)。初期バンドル 1MB 台、画像は章ごとに遅延読み込み
- 1ターン(問題表示 → 入力 → 判定 → 演出)が 10〜20秒で回る。判定は即時(100ms以内)

### 6.4 セキュリティ
- GAS エンドポイントは共有トークンで保護(完全な防御ではないが、無関係な書き込みを防ぐ)
- クライアント側の改ざん(レベル書き換え等)は許容する(成績評価には使わない)

### 6.5 保守性・拡張性
- 章・敵・問題テンプレート・会話は **データファイルの追加** だけで増やせる
- キャラ名は1ファイル(`characters.ts`)にまとめ、後から一括変更できる
- 2年版・3年版は同じリポジトリ内で「学年データ」を切り替える構成(エンジンは1つ)

### 6.6 品質
- 問題生成・判定は自動テストで検証(F52)。前回と同じく「表示された式を別の方法で評価して答えと照合」
- ブラウザ操作の確認は Chromebook 相当の解像度(1366×768)で行う

### 6.7 アクセシビリティ
- キーボードだけで戦闘が完結する(Enter で決定、数字キーで入力、H でヒントなど)
- 「動きを減らす」設定で揺れ・点滅を止める(OS設定も反映)

## 7. 技術選定

### 7.1 採用技術

| 領域 | 採用 | 理由 |
|---|---|---|
| フロントエンド | **TypeScript + Vite + Preact** | 画面は「フォーム・テキスト・ボタン」が主体(数式入力・会話)なので DOM ベースが最適。Preact は React 互換で小さく、生成AIとの相性も良い。型があるとデータ駆動の破綻を防げる |
| 状態管理 | シーンスタック(Title / Login / Map / Town / Battle / Talk / Status)+ 単一のセーブ状態オブジェクト | RPG の画面遷移をスタックで表すと「戦闘中に会話→戻る」が自然に書ける |
| 数式表示 | **KaTeX**(ローカル同梱) | 分数・√・累乗を教科書どおりに表示。CDN 依存を避ける |
| 数式判定 | **自作エンジン**(有理数演算 + 多項式正規化 + √簡約) | 判定対象は中学範囲に限定されるので自作が最も確実で軽い。§7.3 |
| 図形・グラフ | インライン SVG(自作の小さな描画ヘルパ) | 角度・おうぎ形・座標平面・ヒストグラムを座標指定で描く |
| バックエンド | **Google Apps Script Web アプリ + スプレッドシート** | 無料・サーバー管理不要・教師の管理操作がシートで完結・Chromebook/学校ドメインと相性が良い |
| ホスティング | **GitHub Pages**【仮】 | 無料、`git push` で更新。学校のフィルタで `github.io` が開けるか要確認(§9) |
| テスト | Vitest | 問題テンプレートの大量生成検証、判定エンジンの単体テスト |
| 素材 | AI画像生成(静止画)+ プレースホルダ / 音源はフリー素材 | §4-I |

### 7.2 検討した代替案

| 案 | 却下理由 |
|---|---|
| Phaser などのゲームエンジン | 数式の入力フォーム・テキスト主体の UI と相性が悪い。Canvas 上の日本語入力は面倒。ノード式マップと立ち絵バトルに物理・スプライトエンジンは不要 |
| Vanilla JS(前回と同じ) | 型なし・コンポーネントなしで画面が増えると前回と同じ肥大化を招く |
| React(本家) | Preact で十分。バンドルが小さい方が学校回線に優しい |
| Svelte | 良い選択肢だが、エコシステムと生成AIの出力の安定性で Preact/React を優先 |
| mathjs / Algebrite(数式判定) | バンドルが大きい、同値判定が主目的の設計ではない、中学範囲の「答えの形」(既約分数、a√b 形)の判定は自作の方が制御しやすい |
| Firebase / Supabase | 無料枠はあるが、プロジェクト管理・認証設定・学校フィルタの懸念が増える。教師がシートで運用できる GAS の方が総コストが低い |
| GAS の HtmlService でゲーム本体も配信 | Google ドメインなのでフィルタには強いが、iframe サンドボックス・表示速度・ファイル分割の制約が大きい。**GitHub Pages が学校で開けない場合の代替案**として残す |
| localStorage のみ(サーバーなし) | 管理 Chromebook はサインアウトで消える可能性が高い。教師の解放制御・進捗確認もできない |

### 7.3 数式判定エンジンの範囲(F44)

| 段階 | 対応する形 | 必要になる学年 |
|---|---|---|
| 1 | 有理数(整数・小数・分数・負)、複数値、選択式 | 1年(必須) |
| 2 | 1変数〜多変数の多項式の同値判定(2x+3, 3a−2b+1, x²+2x など)。係数は有理数 | 1年(文字と式)・2年(式の計算) |
| 3 | 単項式の積・商(3a²b)、分数式の簡単な形 | 2年 |
| 4 | 平方根の簡約(a√b + c√d 形)、有理化 | 3年 |
| 5 | 因数分解形の判定(積の形になっているかを構文的に確認 + 展開して同値) | 3年 |

入力は「文字列 → トークン → 構文木 → 正規形」に変換して比較する。表示は KaTeX。
